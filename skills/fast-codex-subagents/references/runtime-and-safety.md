# Fast Codex Subagents Runtime and Safety

## Preferred app-server backend

When `backend` is `auto`, a single bounded independent task selects direct Codex `exec`; dependent or complex tasks use app-server. An explicit backend overrides this routing. The app-server backend runs one `codex app-server --listen stdio://` process per task. It hosts separate logical threads with separate histories; it does not share the parent conversation heap. A standard-library `asyncio` supervisor uses one JSONL reader and a serialized writer, with distinct pending-client-response and server-request maps. Events and private logs are associated with their thread and turn IDs. Shared contracts and completed dependency reports are bounded before they cross roles.

The adapter is experimental and accepts only releases in the fixture-tested Codex CLI registry (currently 0.162.1). A candidate numeric version range alone does not authorize execution; follow [the upgrade procedure](codex-upgrade.md). Before launch, `doctor` inspects the installed version and options, runs `app-server generate-json-schema`, checks the schema against the adapter's required methods and request shapes, and calls `model/list` to check available models, reasoning effort, and service tiers. `default` is the protocol's explicit standard-route sentinel, not a catalog tier ID; Fast `priority` must appear in the selected model's catalog. These checks make no model inference and do not prove an individual turn's provider-side tier. An unverified schema, version, model, effort, or requested Fast tier blocks launch. There is no automatic standard-tier retry or backend fallback.

Threads request `approvalPolicy: on-request` and `approvalsReviewer: auto_review`. Writers use `workspace-write`; reviewers use `read-only` plus a read-only, network-disabled turn sandbox. The supervisor never blanket-approves a request. It surfaces command/file/permission approvals, tool user-input prompts, and MCP elicitation requests as pending actions. A reply requires the current request, thread, and turn IDs and a validated method-specific payload. Guardian review events are recorded separately from a user's explicit response.

For each worker, status keeps three distinct facts: requested tier (`priority` for Fast or `default` otherwise), effective thread tier reported by app-server, and upstream execution, which remains `unverified` without provider telemetry. A reported null effective tier for a requested `default` route is recorded as effective `default`, while the original null is retained as the reported value. Token usage and cached-token fields are recorded only when supplied by app-server. The local feature list and model catalog are capability evidence, not proof of an individual session's Fast execution.

The task owns an authenticated loopback control endpoint bound to `127.0.0.1`, with a maximum of 24 concurrently serviced control connections and a 45-second bounded handler wait. App-server RPCs, stdio writes and process shutdown have finite timeouts; a timed-out write or steering action is never automatically replayed. Pending approval requests are capped at 64. Steering records a bounded per-turn fingerprint/idempotency key before submitting the request, and explicitly rejects repeated payloads or keys. A protected discovery file identifies its port; separate random read and control capabilities live in a private file and are never printed. `status` and `events` use read-only access. `steer`, `interrupt`, `reply`, and `recover` require explicit commands and validate current IDs; each successful action returns an acknowledgement. The parent chat polls this endpoint through a tool or CLI and receives no unsolicited context injection. Reconnecting with `resume` talks to the existing supervisor and does not create a second writer or app-server.

Live `status` and `resume` return a compact projection: `event_history` describes the retained event window instead of embedding `control_events`. The latest 20 guardian review summaries and their total count are included; private status and logs retain the full recorded data. Read history with `control events`; pass each page's `next_seq` as the next `--after-seq` while `has_more` is true. `latest_seq` is the current end of the retained stream, not the pagination cursor. Pages are bounded by serialized UTF-8 bytes as well as the requested count. Oversized single records return a bounded error directing the operator to private artifacts.

Routine work-item progress and token-usage notifications are immediately appended to private event history, while their polled status snapshots are coalesced (up to 200 ms). Submission intents, pending approval changes, terminal transitions, and recovery transitions retain immediate durable writes; the pending-request authority file is rewritten only when its contents change. A persistence failure requests recovery rather than being silently swallowed.

A dependency's outcome is consumed only after its worker coroutine has settled, including any final-report read required after a completed-turn notification. A delayed report does not prematurely block dependent roles. A failed report read or a genuinely absent report still prevents dependents from starting; independent roles can continue.

If the app-server or supervisor stops, reconcile the persisted logical thread and turn state before continuing. Recovery resumes saved threads, reads their history, and confirms whether each submitted turn is active, terminal, or uncertain. It never replays an uncertain turn or starts a duplicate thread. If state cannot be proven, the task remains blocked for a deliberate user decision. A worker failure is isolated to its role and dependent roles; independent ready roles may continue.

## Explicit exec fallback

Set `"backend": "exec"` only when the user or project selects the fallback. The approved argument-array pattern is:

```text
codex exec -C WORKSPACE -m MODEL -c model_reasoning_effort="max" -c service_tier="fast" --enable fast_mode --approve-for-me --json --color never -o FINAL_REPORT -
```

For a worker that opts out of Fast, the helper replaces the Fast arguments with `-c service_tier="default" -c features.fast_mode=false`. This explicitly overrides inherited user/project Fast settings without changing those configuration files. Mixed teams receive a separate route selection for each worker.

The helper substitutes the selected effort and report path and sends the prompt on stdin. Reviewers use `-s read-only` instead of `--approve-for-me`. CLI flags and `features list` show the requested configuration only. Effective/upstream Fast execution remains unverified unless the worker event stream contains correlated evidence. Exec fallback does not provide app-server steering or turn-scoped server-request replies. A rejected option or failed launch is reported without changing backend, tier, or sandbox.

Exec status checks correlated effective-route evidence for opted-in and opted-out workers independently. A worker mismatch takes precedence over matching workers in the task summary. Per-worker `fast.effective` remains `unverified` without evidence; the legacy `not_requested` task label describes an opt-out, not verified standard execution. Upstream execution remains unverified without provider telemetry.

## Process ownership and private runtime

The runtime root retains the established `fast-agents` state namespace for compatibility: `%LOCALAPPDATA%/fast-agents` on Windows, `$XDG_STATE_HOME/fast-agents` when set, or `~/.local/state/fast-agents` otherwise. This state path does not change the current public skill ID. The task stores private prompts, per-role event streams and stderr, final reports, usage, IDs, status, and process identities. Treat these artifacts as source-sensitive. POSIX directories/files use owner-only `0700`/`0600` permissions. Windows applies and verifies a protected owner-only DACL; if the host cannot enforce it, setup fails closed.

Process identity uses Linux `/proc`, Windows process creation time and executable path through `ctypes`, or macOS `libproc`. Workspace locks use `fcntl` or `msvcrt`. Supervisor launch uses platform-specific detached-process flags and never invokes a shell. On Windows, Codex is launched through `codex.exe` or a resolved Node entrypoint; `.cmd`/`.bat` wrappers are not invoked. Launch and recovery refuse to proceed when a prior manager or app-server identity is missing, alive unexpectedly, or unknown.

Watcher cleanup signals only a registered watcher whose task identity and process start identity match. It never targets workers or the app-server. The helper does not promise process-tree termination; it does not use a Windows Job Object. The supervisor is **detached**: closing the parent Codex chat or a `watch` terminal does **not** cancel running workers. Cancellation is explicit via `control interrupt` with the current role/turn IDs. A hung turn requires operator inspection and explicit interrupt; no automatic process-tree kill or non-idempotent retry is attempted. If a worker ignores an interrupt or a write/stop timeout expires, inspect status and reconcile before creating any replacement task. Server shutdown closes the owned stdio and waits for that process with a bounded timeout. If the server outlives its supervisor or identity cannot be proven, no unrelated process is signaled or removed.

Writers can edit only under Codex's workspace-write sandbox, which is broader than their declared file list. Ownership is a coordination boundary in prompts and validation, not a per-file OS sandbox. Review the resulting diff. At startup, tasks with writers make a bounded, read-only Git status snapshot when the workspace is the repository root. After execution, the helper records paths newly dirty since that baseline and highlights those outside declared ownership. This is advisory: concurrent external changes and paths already dirty at startup cannot be attributed, and a successful path check **does not verify tests or acceptance**. `verification_state` therefore remains `not_run` until independent verification exists; a Git-unavailable or nested-workspace audit is `inconclusive`. The helper itself makes no HTTP requests; Codex networking follows the user's normal Codex configuration.

## Codex approval boundaries

| Actor | File access / execution boundary | Approval policy |
| --- | --- | --- |
| Codex writer thread | `workspace-write` sandbox; declared `owns` paths are advisory, not OS isolation | `on-request` plus Codex `auto_review`; requests beyond current authority require an explicit current scoped reply |
| Codex reviewer thread | `read-only` sandbox and network disabled on turn; cannot grant writes | Any write approval is rejected; ordinary read-only review requires no write grant |
| App-server supervisor | Private task state, pending request registry and loopback port; not application source edits | Exact transport epoch/thread/turn/request IDs and separate read/control capability tokens |
| Other local processes / agents | No access is granted by metadata; Codex runtime must be installed and configured | Non-Codex caller hints fail early; environment flags are **not cryptographic proof** of the parent agent |

Never infer per-file isolation from a writer manifest. `acceptForSession` is broader than `accept` and must be approved deliberately; the supervisor does not blanket-approve. See the exact server-request payload with the authenticated `inspect-request` command before a scoped `reply`.

## Worker → supervisor IPC threat model

- **Untrusted or malformed event streams:** Codex app-server JSONL is bounded to 8 MiB per line, validated as JSON objects, and correlated by current thread/turn IDs. Unknown request methods are rejected. Exceptions and transport loss are surfaced instead of triggering automatic action replay.
- **Steering replay / duplicated approvals:** Control requests must include the task's private capability token. Steering uses a durable key and content fingerprint for at-most-one submission attempt per key/payload on the current turn. Concurrent approval responses are claimed before the first await; on uncertain delivery neither is retried silently. This is not a server-provided exactly-once guarantee.
- **IPC resource exhaustion:** Loopback connections, request lengths, pending approval counts, and timeouts are bounded. Local filesystem artifacts and transcripts are sensitive and require owner-only permissions.
- **Host compromise / injected prompts:** Same-user access to protected runtime files may expose control capabilities; a malicious agent or compromised local process must not be treated as a separate security principal. Read-only Codex sandbox and on-request approval semantics are the actual execution constraints, subject to the installed Codex version.
- **Parent exit / cancellation:** The detached task survives a parent session exit. `watch` is non-owning; only an explicit current-turn `interrupt` requests cancellation. Lost responses remain uncertain and are reconciled without replay.
